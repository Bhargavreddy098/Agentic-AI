# First validation: observed paid workflow replacement

This is a proposed experiment, not evidence about conversion, demand, or a chosen price.

## Assumption
A specific reachable cohort has a recurring agent workflow whose supervision, failure recovery, or tool handoffs are costly enough that users will move real work to a local application and pay for the improvement separately from model usage.

## Procedure
1. Recruit people who already execute the same kind of real workflow repeatedly. Do not mix developers, hobbyists, and researchers in one verdict.
2. Ask each person to show their most recent execution and a failed execution using files/history they consent to share. Record what broke, existing workaround, time supervising, recovery time, output verification, current expenditure, and consequences. Do not lead with the proposed platform.
3. Select one repeated bottleneck. Have the person run their normal toolchain on an upcoming task and define output acceptance before testing the prototype.
4. Supply a narrow local prototype using an existing runtime if appropriate. Record setup/migration time, interventions, total model costs, accepted output, and safe handling of a deliberate recoverable interruption. Identify any founder assistance; assisted results do not establish self-service usability.
5. Agree on a real paid-pilot offer individually before delivering continuing value. Pricing is an experimental variable, not a recommendation or a known willingness-to-pay amount. State licensing, model bills, and support terms clearly.
6. Observe whether people initiate the next scheduled real task without prompting and whether they pay to continue. Keep failed and abandoned runs in the denominator. Check whether they would still buy if restricted to one model/provider; this separates outcome value from enthusiasm for provider choice.

## Proposed decision rule
For an initial directional test, recruit eight qualified users from one cohort. Proceed to the next limited development tranche only if at least four independently use the prototype for three naturally recurring tasks over a period covering those repetitions, and at least three make an actual paid-pilot purchase at a price justified against observed support/update costs. These counts are founder-selected gates, not statistically representative estimates or predicted conversion. Set comparative acceptance criteria from observed baseline before prototype use; require an improvement in accepted-output economics or supervision/recovery effort without unacceptable regressions. Keep the founder's time and model spend in the comparison.

If the problem is infrequent, existing tools solve it after minor setup, users do not return without chasing, or payment disappears after novelty, halt broad platform expansion. Change the workflow/cohort hypothesis, rather than expanding feature scope to explain away the result.

## Unknowns and follow-on work
- Exact competitors and best alternatives for the selected task: founder-competitors plus hands-on comparison.
- Objections and segment hypotheses: founder-consumer can help generate hypotheses; simulated purchases cannot validate actual demand.
- Sustainable license/support economics: founder-cfo after measured support costs.
- Packaging and price: founder-pricing after real buying evidence. Do not invent a demand curve from simulated answers.
